# EMF security, HIPAA safeguard, and NIST alignment audit

Baseline: `52f16384`. Review date: 2026-09-25. Status: engineering review with code hardening; deployment controls require owner validation. No certification, legal-compliance determination, penetration test, or production authorization is asserted.

## Scope and method

Reviewed security/encryption/content storage, console composition and external calls, workflow persistence, Veterans reviewer provenance/rendering, temporary material, SQLite security auditing, threat-model documentation, and dependency metadata. Findings distinguish demonstrated code defects from configuration/process gaps. Regression fixtures use synthetic content. No Azure OpenAI or Key Vault calls were made; no medical content was sent externally. Public HHS/NIST sources and public NuGet vulnerability metadata were consulted. Existing medical files, databases, permissions, backups, and generated `EMF_Output` files were not altered by this security review.

This supplements [THREAT_MODEL.md](docs/THREAT_MODEL.md), [NIST_CONTROL_MAPPING.md](docs/NIST_CONTROL_MAPPING.md), [SECURITY_AUDIT_OPERATIONS.md](docs/SECURITY_AUDIT_OPERATIONS.md), and [PROTECTED_BACKUP_RECOVERY.md](docs/PROTECTED_BACKUP_RECOVERY.md). Their historical test counts are not current assurance evidence. The threat model already treats insider access, logs, metadata, backups, provider routing, and compromised dependencies as threats; this audit tests concrete implementations of those boundaries.

The HIPAA Security Rule concerns administrative, physical, and technical safeguards for regulated entities. This report uses those concepts as an engineering framework; applicability and organizational obligations require a separate assessment. [HHS Security Rule overview](https://www.hhs.gov/hipaa/for-professionals/security/laws-regulations/index.html).

NIST SP 800-66 Rev. 2 provides implementation guidance and crosswalks for HIPAA safeguards. The mappings below are reviewer judgments about relevant control objectives, not proof that an entire control is satisfied. [NIST SP 800-66 Rev. 2](https://csrc.nist.gov/pubs/sp/800/66/r2/final). CSF function/category references use the [NIST Cybersecurity Framework](https://www.nist.gov/cyberframework); SP 800-53 references identify control families/objectives from the [NIST control catalog](https://csrc.nist.gov/pubs/sp/800/53/r5/upd1/final).

## Data-flow and trust boundaries

| Data | Processing / storage | Boundary and required protection |
|---|---|---|
| Original medical documents, source filenames and source paths | Input filesystem, extraction/rasterization, ingestion | PHI may exist in filenames and metadata as well as document bodies. Input access and parser isolation matter. |
| Derived notes and attachments | Artifact content store, provenance database | Production composition uses envelope encryption; raw filesystem store remains a lower-level abstraction and must not be substituted as a production plaintext fallback. |
| Claims, conditions, recognition terms, progression, selections, summaries and lineage | SQLite repositories | Metadata can itself be PHI. Artifact encryption does not encrypt SQLite, WAL/SHM, exports, or backups. |
| Decrypted note text, native page pixels, DOCX/PDF bytes | Managed memory, conversion workspace, generated output | Memory, process dumps, temporary files, outputs and retained backups remain sensitive after correct encryption at rest. |
| Intelligence request/response | Authorization/routing, optional Azure provider, persisted derived result | Live gate and validated endpoint are necessary but do not independently establish purpose authorization, minimum necessary data, tenant approval, or provider retention policy. |
| Security events and diagnostics | Local audit SQLite, optional Azure Monitor | Identifiers/correlation are not necessarily anonymous. External facts must use approved bounded operational data. |
| Keys | Random DEKs in memory, wrapped DEKs in envelopes, versioned KEKs in configured vault | Key-use permission can expose plaintext even without key export. Historical keys, rotation, revocation and recovery must be governed. |

No automatic PHI classifier can be assumed authoritative. Classification and permitted destination are security policy inputs; a caller assigning a less restrictive classification is a trust-boundary risk. Source content and model output remain untrusted, and reviewer text must preserve the distinction between factual evidence and independent medical/legal/adjudicative conclusions.

SEC-01 intentionally changes legacy artifact access: do not automatically upgrade an unbound envelope merely because it occupies an artifact filename. A migration must establish the intended artifact from independently trusted lineage/fingerprint evidence, decrypt only in an authorized environment, re-encrypt bound to that identity, and preserve backups/audit evidence. Rewrapping a key alone does not convert an unbound envelope into an identity-bound one. No live keys or envelopes were migrated during this review.

SEC-02 is a defense against pre-existing path redirection, not a portable race-free filesystem sandbox. A hostile principal able to replace directories between validation and open can still race pathname operations. Private, owner-controlled roots and ancestors remain mandatory; service deployment needing hostile shared directories would require OS-specific handle-relative/no-follow operations. Intentional symlink roots must be replaced by their approved physical path. Deleting files is not guaranteed secure erasure.

The core hardening report additionally covers package membership, later-evidence leakage, lineage contradictions, reviewer boundaries, semantic reuse and migrations. These are integrity and minimization controls as well as functional correctness. Package membership must remain persisted-authoritative; source ambiguity must not produce nearby or parent evidence as a silent substitute.

Cryptography reviewed uses AES-256-GCM with random 32-byte DEKs, 12-byte nonces and 16-byte tags; identity-bound authenticated context and versioned key references protect new envelopes. DEKs are cleared in finally blocks. This is algorithm/implementation evidence, not a claim that the deployed cryptographic module is FIPS validated. Source SHA-256 fingerprints are integrity checks, not digital signatures or authenticated provenance against an attacker who can rewrite both bytes and metadata. Same-artifact rollback also requires a trusted version/history anchor beyond identity binding.

## Read-only local permission observations

Only modes/counts were recorded; medical filenames/content were not copied into this report. ACLs, group membership, mounted-volume encryption, remote backup encryption and root/administrator access were not independently validated.

| Location | Directory mode | Observation |
|---|---|---|
| Home directory | 0750 | Other users blocked absent ACL/root access; members of the home group can traverse. |
| `EMF_Input` | 0700 | Owner-only parent; many descendant files are0644/0664 or executable/read-only and would be less protected if copied elsewhere. |
| `EMF_Output` | 0775 |79 files 0600; 1102 files 0664; 22 files 0644; further files have executable/group-readable modes. Includes 22 SQLite-named files. |
| Project `.emf-local` | 0775 |75 files 0644, 69 files 0664, 10 files 0600; 61 SQLite-named files. |
| Discovered `.emf-local` artifact-content directories | 0775 | Existing directories require access review; creation-mode hardening does not rewrite them. |

Counts are a point-in-time inventory including retained backups and can change independently of source. Preserve backups; review ownership/ACLs and choose an approved sharing model before changing live permissions. Future generated packages should be owner-only by default unless a controlled recipient workflow specifies otherwise. ZIP is packaging, not encryption: an unencrypted archive containing PHI requires the same controls as its contents.

## Input, injection, and supply-chain observations

- Archive processing reads bounded entry streams into memory and stores under generated artifact IDs. Untrusted entry names remain metadata and can still be sensitive. The content-store path guard must not be bypassed by future extraction features.
- Reviewed SQLite paths use parameterized data commands and structured connection strings. No concrete SQL-injection defect was demonstrated in this review; this is not exhaustive query fuzzing.
- JSON/XML/office parsers use established libraries rather than arbitrary runtime type instantiation. Limits exist for several document paths; exhaustive malformed-format CPU/memory testing remains open.
- Subprocess conversion uses `UseShellExecute=false`, `ArgumentList`, isolated profiles and timeouts. This prevents shell interpolation of filenames but does not sandbox the parser process or block network access.
- Key Vault accepts a configured HTTPS Azure vault root with explicit key/version validation; production uses managed identities and no application-side key export. Actual RBAC, purge protection, firewall/private endpoints and rotation were not exercised.
- Targeted source/test searches did not demonstrate a committed production credential; this was not a full-history secret scan. Do not interpret absence of pattern hits as assurance about secrets in backups, binary fixtures, process environment or historical commits.
- Public NuGet audit: `dotnet list EMF.sln package --vulnerable --include-transitive --format json`, exit 0, 25 projects, 0 vulnerability entries, 0 reported problems. Output `/tmp/emf-hardening-vulnerabilities.json`. This covers known feed advisories for resolved NuGet packages, not all future/unknown flaws, native tool packages, operating-system packages or deployment configuration. Repeat in CI; maintain existing pinned/Dependabot/CodeQL/SBOM controls and remediation ownership.
